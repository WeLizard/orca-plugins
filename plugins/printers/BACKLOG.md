# Print Farm — бэклог

Print Farm — самостоятельный плагин, не часть FilamentHub. Бэклог живёт здесь, а
не в очереди FilamentHub: так решено в `ADR_PRINTERS_PLUGIN_BOUNDARY`.

## Баги при живом использовании

Владелец наблюдает дефекты, конкретные симптомы пока не зафиксированы. Без списка
воспроизводимых шагов работа по исправлению не стартует — иначе исправляется
догадка, а не дефект.

## `orca.printer_agent` — стоит ли переходить на хостовый путь

В plugin API OrcaSlicer появился тип возможностей `orca.printer_agent`
(`src/slic3r/plugin/pluginTypes/printerAgent/`). Он покрывает ровно ту зону,
которую Print Farm сейчас несёт сам: обнаружение принтеров в сети, обмен
сообщениями с устройством, привязка, запуск печати.

Проверено чтением исходников `main` (клон `F:\orca-upstream`, состояние
2026-07-24):

- регистрируется как подмодуль plugin API без видимых ограничений по типу
  плагина;
- интерфейс включает обнаружение по сети, обмен сообщениями, привязку и отвязку
  устройства, запуск печати (локально, через облако, с SD-карты), получение
  информации о филаменте и режим её синхронизации (нет / подписка / опрос),
  работу с сертификатами устройства;
- терминология заметно ориентирована на сетевой агент Bambu (идентификаторы
  устройств, раскладка AMS, привязка по коду). Применимость к Moonraker и Voron —
  открытый вопрос, а не данность.

Вывод нужен предметный: по каждому сценарию «применимо / только Bambu / требует
доработки хоста», с опорой на код и живую проверку, а не на названия методов.
Возможности хоста различаются между сборками, поэтому адаптация обязана сохранять
работу на сборке без этого API.

## Порядок

1. Собрать симптомы багов — список воспроизводимых дефектов.
2. Закрыть подтверждённые дефекты без регресса.
3. Разобрать `printer_agent` на применимость.
4. Заменить самодельную логику там, где хостовая не хуже.

Работа отложена намеренно, чтобы не отвлекать от основного проекта.
